A security checklist for a new NestJS API

The small set of defensive defaults I want in place before an API serves its first real user.

In this article

  1. Validate request shape
  2. Make authorization explicit
  3. Protect operational surfaces
  4. Test negative paths

A framework gives an API structure, not a security guarantee. Before shipping a NestJS service, I want its boundaries, defaults and failure modes to be deliberate.

1. Validate the shape of every request

Use DTOs and a global validation pipe with transformation disabled unless you need it deliberately. Reject unknown properties rather than silently accepting fields the endpoint never intended to handle.

new ValidationPipe({
  whitelist: true,
  forbidNonWhitelisted: true,
  transform: false
})

Why allowlists matter

An allowlist makes the accepted contract visible. It also prevents a new client field from quietly reaching business logic before the endpoint has decided what that field means.

2. Make authorization explicit

Authentication guards answer “who are you?” Authorization answers “may you perform this action on this resource?” Keep both questions visible in the route or service, and verify ownership or role permissions before returning records.

Authentication identifies the caller; authorization limits the caller’s power.

3. Protect operational surfaces

  • Set safe HTTP headers with Helmet.
  • Configure CORS for known origins instead of allowing every origin by default.
  • Rate-limit login, password reset and other expensive or sensitive endpoints.
  • Keep secrets in environment configuration and out of logs.

4. Fail without leaking

Clients need useful status codes, not stack traces or database details. Log enough context server-side to investigate a failure, while keeping tokens, passwords and personal data out of those logs.

5. Test the negative paths

The useful tests are often the requests that should fail: an unknown field, a missing role, another user’s resource ID, an expired token and a request that exceeds the rate limit. A small negative-path suite catches regressions early.
