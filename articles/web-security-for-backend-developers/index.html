Web security for backend developers: start with the request

A practical mental model for tracing input through an API and finding the assumptions that become vulnerabilities.

Security work becomes less mysterious when you follow the same path a request takes through the application. A user sends data, the server interprets it, business rules run, and a response is returned. Every transition is a chance to validate an assumption.

Start with the trust boundary

Anything arriving from a browser, mobile client, webhook or third-party service is untrusted. Authentication can tell you who sent a request; it does not make the values inside that request safe.

For each endpoint, write down the boundary explicitly:

  • What identity is attached to the request?
  • Which fields are allowed and what types do they have?
  • Which records may this identity read or change?
  • What happens when a field is missing, duplicated or unexpectedly large?

Trace input all the way to a side effect

Validation at the controller is important, but it is not the whole review. Follow the value into queries, file operations, logs, templates and outbound requests. A safe type at the edge can still be used unsafely later.

request → authentication → validation → authorization
        → business logic → database / service → response

This simple map makes review concrete. If authorization is missing between authentication and a database lookup, the endpoint may have an object-level access control problem. If a value reaches a query by string concatenation, validation did not solve the real issue.

Prefer narrow, boring controls

Use allowlists for fields, parameterized database APIs, output encoding at the rendering boundary, and explicit authorization checks close to the data they protect. These controls are easier to test than a single global “security” layer that has to understand every feature.

Turn the review into a habit

Pick one endpoint and ask the same questions every time. Over time, the checklist becomes part of design rather than a last-minute audit. The goal is not to eliminate every possibility; it is to make unsafe assumptions visible early.
